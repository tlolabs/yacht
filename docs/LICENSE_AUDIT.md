# Licensing and provenance audit

Audit updated 2026-09-24. This review distinguishes ownership of YACHT source, linked dependencies, redistribution of Microsoft files, and SignPath Foundation eligibility. It records evidence; it is not a legal opinion.

## Decision

**Thomas Lothian's original source and artwork are now offered under GPL-3.0-or-later without relicensing Microsoft code.** The presence of WinUI 3 or a Microsoft runtime does not by itself change the license Thomas may grant for code he owns. The Git history identifies one author identity and no contributor-authored commits; a Git author string cannot rule out an employer or other ownership claim.

**The currently published Windows portable ZIP is a separate question.** It bundles Microsoft files with terms that are not all open-source licenses. That does not make Thomas's source GPL-incompatible, but conveyance of an *unexcepted combined Windows executable* may need a GPLv3 System Libraries analysis or a narrow linking permission. Mere aggregation of separate files in a ZIP is not, by itself, a GPL license conflict; the WinUI application has actual linkage and runtime calls to consider. The exception does not automatically cover separately shipped WinUI 3 files. SignPath applies its own rules and has final discretion. Keep Microsoft terms separate; do not label the Microsoft bytes GPL or claim the current Windows ZIP is SignPath-qualified.

## GPLv3 and SignPath are separate tests

GPLv3 [section 1](https://www.gnu.org/licenses/gpl-3.0.html#section1) defines a System Library by its relationship to the normal packaging of a major operating-system/compiler/interpreter component and its function. It excludes qualifying libraries from Corresponding Source. The [GNU FAQ](https://www.gnu.org/licenses/gpl-faq.en.html#SystemLibraryException) applies the exception to GPL-incompatible system libraries, and its [Visual C++ runtime example](https://www.gnu.org/licenses/gpl-faq.en.html#WindowsRuntimeAndGPL) distinguishes an installed system runtime from shipping those DLLs with the program. The rule is fact specific; Microsoft provenance alone neither proves nor defeats it. Nothing in the present evidence shows that the self-contained, app-local Windows App SDK, Windows ML, or SDK projection files are normally packaged as part of Windows. A separate runtime installed for all apps would improve the argument, but is not automatically a System Library merely because it is installed separately.

GNU's [guidance on incompatible libraries](https://www.gnu.org/licenses/gpl-faq.en.html#GPLIncompatibleLibs) permits a copyright holder to give a narrowly named GPLv3 section 7 linking permission if one is needed. Such permission would apply only to Thomas's code and specified libraries; it would neither relicense Microsoft files nor make a proprietary bundled component eligible for SignPath. Do not add a blanket Microsoft exception without identifying the exact still-required files and their license terms. A lawyer or the Free Software Foundation can review the final combination before a new Windows release.

There is also a **Microsoft redistribution condition independent of GPL**: Windows App SDK and Windows ML sections 3.b.ii–iii require downstream terms protecting Microsoft and indemnity. The historical portable ZIP includes neither the package license files nor an end-user agreement mechanism for those clauses. Copying license/notice files into a future ZIP corrects notice availability but does not, by itself, prove those contractual conditions are met. Moving the proprietary runtime to a separately installed Microsoft package is the smallest route that avoids redistributing those runtime bytes in YACHT's portable ZIP; Microsoft controls installation terms for its own runtime. Any residual app-local Microsoft files still need exact review.

[SignPath Foundation's OSS conditions](https://signpath.org/terms.html) separately require an OSI-approved license for all components and forbid proprietary components in signed packages **except System Libraries**, referring expressly to GPLv3 section 1. Thus GPL-or-later for YACHT source satisfies only the project's own-license part. MIT .NET packs, BSD-3-Clause WebView2 SDK files, and MIT Tensors meet the open-source license aspect; their inclusion still carries notice and signing-scope obligations. App-local proprietary Windows App SDK, Windows ML, and SDK projection files have not been established as exempt. Even if GPL conveyance is solved by a section 7 permission, SignPath may still reject a package containing them. Its terms also distinguish signing YACHT binaries from including unsigned upstream binaries; do not sign Microsoft DLLs using a Foundation certificate.

## Smallest practical Windows path

1. Keep WinUI 3 and the GPL-3.0-or-later source declaration. Do not change project license because of Microsoft redistributables.
2. Test a **framework-dependent** Windows build: set `WindowsAppSDKSelfContained=false` and `.NET SelfContained=false`, install the matching Windows App Runtime, .NET 8 Desktop Runtime, Visual C++ runtime, and WebView2 Evergreen Runtime separately, then run the native UI and packaging tests on both x64 and ARM64. [Microsoft documents this deployment model](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/deploy-unpackaged-apps). Record the new ZIP's file hashes and check for residual bootstrapper/projection files. The portable app would need clear prerequisites and an installer or user-directed links. This may add a first-run setup step; it should not materially change the application UI or conversion function. It remains a testable option, not a proven replacement today.
3. Exclude the five unused Windows ML files if the App SDK permits it; verify launch, preview, and conversion. This removes the clearest unnecessary proprietary payload even if a self-contained build is retained.
4. Preserve the applicable `license.txt`, `NOTICE.txt`, and `.NET` third-party notices alongside any runtime files that remain bundled. The historical ZIP omitted those package notices; correct future builds rather than altering old releases.
5. If necessary after the reduced inventory, review a precisely scoped GPLv3 section 7 linking permission for required non-System Libraries. Separately present the exact reduced inventory to SignPath for a decision on its System Libraries exception. If SignPath rejects it, use another signing provider; that does not require abandoning GPL for YACHT code.

The Windows packaging script uses `--self-contained true` and `<WindowsAppSDKSelfContained>true</WindowsAppSDKSelfContained>`, so these are material to redistributed Windows binaries. SDK build tools are build inputs; they are not automatically part of the output.
- macOS uses Apple system frameworks (SwiftUI, AppKit, WebKit, Foundation) and Linux uses system GTK, libadwaita, WebKitGTK, PyGObject, Python, and glibc. These are not vendored in the tracked tree. Linux `.deb`/tar packages rely on those system packages rather than bundling them. Their licenses and installed versions remain the distributors' responsibility.
- The generated Xcode project is produced by `script/generate_project.py`; generated icons and project metadata do not acquire a new author/license merely by generation. The root GPL text retains the Free Software Foundation's copyright and must remain verbatim.

## Remaining decisions

The own-code GPL-or-later change is made. Before another Windows release, test and inventory the reduced/framework-dependent distribution, resolve any residual linking question, and include required notices. A SignPath decision is independent of GPL compliance. No exact Microsoft component identified here warrants changing the license of Thomas's original code. Dependency-license warnings should remain visible without failing routine build CI; mismatched project SPDX declarations may fail compliance CI.
